# Biz Forecaster — 소상공인 AI 수요예측 · 이상탐지 플랫폼

빵집 판매 데이터를 기반으로 수요를 예측하고, 매출 이상을 탐지하며, 그 원인을
SHAP으로 설명하는 Streamlit 애플리케이션입니다.

---

## 빠른 실행

**Windows** — `실행하기.bat` 을 더블클릭하세요.
Python 자동 탐색 → 가상환경 생성 → 라이브러리 설치 → 앱 실행까지 한 번에 처리합니다.
처음 실행은 10~30분 걸립니다(prophet·xgboost 컴파일). 두 번째부터는 즉시 실행됩니다.

**직접 실행하려면**

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m streamlit run app.py
```

> Python **3.11 권장**. 3.13/3.14에서는 `prophet`·`xgboost` 설치가 자주 실패합니다.

첫 화면에서 **회원가입 → 이메일 인증 → 로그인** 후 데이터를 업로드합니다.
데이터가 없으면 사이드바의 **"동봉된 예시 데이터로 둘러보기"** 를 체크하면 됩니다.

## 화면(소상공인)과 분석(개발자)을 갈라놓은 이유

관리도·오탐률·ARL0 같은 말은 소상공인에게 아무 도움이 안 됩니다. 반대로
"평소보다 79% 적게 나갔습니다 → 재고가 남았을 수 있습니다"는 통계를 몰라도
바로 행동할 수 있습니다. 같은 계산이지만 받는 사람이 다르면 다르게 보여줘야 합니다.

그래서 층을 갈랐습니다:

| 층 | 파일 | 대상 | 내용 |
|---|---|---|---|
| 판단 | `detect/control_charts.py` | — | 통계적으로 이상한가 |
| 번역 | `detect/alerts.py` | 소상공인 | 그래서 재고를 어떻게 하라는 것인가 |
| 검증 | `detect/evaluation.py` | 개발자 | 이 판단이 얼마나 믿을 만한가 |

**앱 화면에는 통계 용어가 한 글자도 나가지 않습니다.** 관리도 파라미터 슬라이더,
오탐/미탐 채점표, ARL0 비교는 전부 화면에서 뺐고 `analyze_detectors.py` 로 옮겼습니다.

```bash
.venv\Scripts\python.exe analyze_detectors.py           # 성능 분석 전체
.venv\Scripts\python.exe analyze_detectors.py --save    # CSV + monitoring.db 로 저장
.venv\Scripts\python.exe analyze_detectors.py --item 크루아상 --magnitude 2.0
```

### 알림이 소음이 되지 않게

이상탐지의 가장 흔한 실패는 "알림이 너무 많아 아무도 안 보는" 것입니다. 세 가지를 걸었습니다:

1. **20% 미만 차이는 버립니다.** 통계적으로 유의해도 현장에서 의미 없는 수준입니다.
2. **요일을 맞춰 비교합니다.** 토요일은 토요일하고만 비교합니다. 전체 평균과 비교하면
   멀쩡한 주말이 매번 이상으로 잡힙니다.
3. **이유를 아는 날은 뒤로 밉니다.** 크리스마스 시즌 급증을 '긴급'으로 띄우면 정작
   원인 모를 급감이 그 아래 묻힙니다. 시즌·공휴일·날씨로 설명되는 날은
   `🗓 이유를 아는 날` 로 따로 묶어 아래에 두고, **원인 불명을 맨 위**에 올립니다.

예시 데이터 기준 최근 30일 알림 25건 중 23건이 크리스마스 시즌이었고,
실제로 확인이 필요한 건 2건이었습니다.

## 화면에서 뺀 것 — 왜, 어디로

소상공인이 매일 볼 화면과 "이 방법이 맞는지 증명하는 화면"은 다릅니다. 후자를 화면에서
빼고 스크립트로 옮겼습니다. 연구 자료가 사라진 게 아니라 실행 위치만 바뀐 것입니다.

| 원래 탭 | 지금 | 이유 |
|---|---|---|
| 📐 탐지 성능평가 | `analyze_detectors.py` | 오탐률·ARL0는 개발자 지표 |
| 🔗 품목간 수요연쇄 (H2′) | `analyze_item_chain.py` | 가설 검증용, 운영에 불필요 |
| 🌦 이벤트 우선 예측 (H1) | 탭 유지, **맨 뒤 + 개발자 전용 표시** | What-if 채팅의 근거 모델이라 남김 |

```bash
.venv\Scripts\python.exe analyze_item_chain.py --by category
.venv\Scripts\python.exe analyze_item_chain.py --lead 음료 --lag 식사빵
```

> H2′ 스크립트로 옮기면서 버그를 하나 고쳤습니다. `grangercausalitytests()` 의 `verbose`
> 인자가 statsmodels 0.15에서 제거됐는데 코드가 계속 넘기고 있어 `TypeError` 가 났고,
> `except Exception` 이 이를 삼켜 **p-value 가 항상 빈칸으로 나오고 있었습니다.**
> 고친 뒤 42개 조합 중 23개가 Granger 인과성 검정(p<0.05)을 통과했습니다.

### 2. 셀프마스킹 방지

모든 관리한계는 `series.shift(1)` — 즉 **전날까지의 값으로만** 계산합니다.
당일 값을 자기 기준선 계산에 넣으면, 이상치가 자기 기준선을 끌어올려 스스로를
정상으로 만들어 버립니다.

### 3. 잔차 관리도 — 관리도의 전제 맞추기

관리도는 "정상일 때 값이 하나의 분포를 따른다"고 전제합니다. 그런데 판매량은
주말에 뛰고 평일에 가라앉아 이 전제가 깨집니다. σ가 요일 간 차이까지 흡수해
부풀고, 관리한계가 그만큼 넓어져 진짜 이상을 놓칩니다.

실제 데이터에서 확인된 효과:

| | 3σ | EWMA | CUSUM | 합의 |
|---|---|---|---|---|
| 원계열 | 7일 | **0일** | **0일** | 3일 |
| 요일 잔차 | 19일 | 21일 | 19일 | 22일 |

원계열에서는 EWMA·CUSUM이 **한 건도 탐지하지 못했습니다.** 요일 프로파일을
제거하니 정상 동작합니다. 반도체 FDC에서 레시피 스텝별 기대 프로파일을 뺀
잔차를 관리도에 올리는 것과 같은 처리입니다.

### 4. 오탐 / 미탐 트레이드오프 (`analyze_detectors.py`)

이상탐지는 "몇 건 잡았다"로 평가할 수 없습니다. 문턱값을 낮추면 무조건 더 많이
잡히기 때문입니다.

- **오탐** (False Alarm, FP) — 정상인데 경보 → 현장이 경보를 무시하기 시작
- **미탐** (Miss, FN) — 이상인데 침묵 → 문제가 그대로 다음 단계로

**정답 라벨이 없는 문제**: 실제 판매 데이터에는 "이 날이 진짜 이상이었다"는
라벨이 없습니다. 그래서 **크기와 시점을 아는 이상을 인위적으로 주입**하고
(`inject_faults`) 탐지기가 잡아내는지 측정합니다. 정답을 아는 문제를 만들어
채점하는 방식이며, 반도체에서 신규 FDC 레시피 검증에 쓰는 방법과 같습니다.

측정 지표:

| 지표 | 뜻 |
|---|---|
| 오탐률 (FAR) | `FP / (FP + TN)` — 정상일 중 헛경보 비율 |
| 미탐률 (MDR) | `FN / (FN + TP)` — 이상일 중 놓친 비율 |
| **실측 ARL0** | `정상일 수 / 오경보 수` — 오경보 한 번까지의 평균 일수 |
| 평균 탐지지연 | 이상 시작 후 첫 탐지까지 일수 |

**ARL0**가 실무에서 가장 직관적입니다. 3σ 관리도의 이론값은 약 370(정상 370일에
헛경보 1회)인데, 실측이 20이면 "3주에 한 번 헛경보"라는 뜻이고 현장은 그 경보를
곧 무시하게 됩니다. 예시 데이터에서 다수결 합의의 실측 ARL0는 **363**으로
이론값에 근접했습니다.

**문턱값 스윕**은 `L`·`h`·`contamination`을 바꿔가며 FAR과 MDR이 어떻게 맞바뀌는지
곡선으로 보여줍니다. 요점은 "최적값 하나"가 아니라 **어떤 값을 골라도 둘 다
좋아지지는 않는다**는 사실 자체입니다. 어디를 고를지는 통계가 아니라 비용이
정합니다 — 헛경보 한 번의 비용과 놓친 이상 하나의 비용 중 무엇이 비싼가.

### 5. 모니터링 연동

탐지 결과는 `monitoring.db`(SQLite)로 내보내집니다.
Grafana가 `grafana-sqlite-datasource` 플러그인으로 직접 읽습니다.

- `daily_metrics` — 일별 값·관리한계·CUSUM 누적값·방법별 탐지 플래그

  (문턱값을 왜 그렇게 정했는지 근거를 남기기 위한 테이블)

## 계정 인증

소상공인마다 로그인해 **자기 매장 데이터만** 보도록 분석 화면 전체를 로그인 뒤에
숨깁니다. 업로드한 파일은 `data/users/<user_id>/` 아래에만 저장됩니다.

- **비밀번호**: PBKDF2-HMAC-SHA256, 계정별 salt, 20만 회 반복. 평문 저장 없음.
  비교는 `hmac.compare_digest`로 타이밍 공격을 방지합니다.
- **이메일 인증**: 6자리 코드, 10분 만료, 5회 시도 제한, 60초 재발송 쿨다운.
  코드도 해싱해 저장하므로 DB를 열어봐도 알 수 없습니다.
- **계정 열람 방지**: 로그인 실패 시 "이메일 없음"과 "비밀번호 틀림"을 구분하지
  않습니다. 구분하면 어떤 이메일이 가입돼 있는지 알려주는 꼴이 됩니다.

외부 라이브러리를 쓰지 않고 표준 라이브러리(`sqlite3`·`hashlib`·`secrets`·`smtplib`)
만으로 구현해, `requirements.txt` 변경 없이 동작합니다.

### 가입 가능한 이메일 도메인

현재 **@gmail.com 계정만** 인증이 가능합니다. 기술적 제약은 아닙니다 — 어느 도메인이든
받을 수 있지만, 개인 Gmail에서 보낸 메일이 다른 서비스(특히 네이버)의 스팸함으로 자주
들어가서, 코드를 못 받고 가입에 막히는 것보다 처음부터 범위를 밝히는 편이 낫다고 보고
제한했습니다.

회원가입 화면에서 다른 도메인을 입력하면 즉시 안내가 뜨고 제출 버튼이 잠깁니다.

열어주려면 `auth/store.py` 의 상수 한 줄만 고치면 됩니다:

```python
ALLOWED_EMAIL_DOMAINS = ("gmail.com",)              # 현재
ALLOWED_EMAIL_DOMAINS = ("gmail.com", "naver.com")  # 네이버도 허용
ALLOWED_EMAIL_DOMAINS = ()                          # 모든 도메인 허용
```

### 이메일 발송 설정

설정하지 않으면 **개발 모드**로 동작합니다 — 메일을 보내지 않고 인증코드를 화면에
바로 띄우므로, 설정 없이도 가입 흐름을 그대로 시험할 수 있습니다.

실제 메일로 받으려면 프로젝트 루트의 `secrets.toml.example`을 참고해
`.streamlit/secrets.toml`을 만드세요. 네이버·구글 모두 **앱 전용 비밀번호**가
필요합니다(일반 로그인 비밀번호로는 SMTP 접속이 거부됩니다).

설정이 맞는지는 앱을 띄우지 않고 따로 확인할 수 있습니다:

```bash
.venv\Scripts\python.exe check_email.py          # 접속·로그인만 확인
.venv\Scripts\python.exe check_email.py --send   # 본인에게 테스트 메일 1통
```

Windows에서는 `이메일설정확인.bat` 을 더블클릭해도 됩니다.
SMTP 오류는 원문이 불친절해서(`Username and Password not accepted`), 이 도구가
원인을 순서대로 짚어줍니다.

> ⚠ 앱 비밀번호는 발송(SMTP)뿐 아니라 **받은편지함 읽기(IMAP)** 권한도 함께 열립니다.
> 개인 메일 계정보다 **발송 전용 계정을 따로 만들어 쓰는 편**이 안전합니다.
> `secrets.toml` 은 `.gitignore` 에 있고 배포 zip 에서도 제외되지만, 폴더를 통째로
> 복사해 전달할 때는 이 파일을 먼저 지우세요.

## 배포 — 깃에 없는 설정을 서버가 어떻게 읽나

`secrets.toml`은 `.gitignore`에 있어 저장소에 올라가지 않습니다. 그러면 배포된 앱은
설정을 어떻게 읽을까요. **그 자리를 배포 플랫폼이 대신 채워줍니다.** 비밀키를 코드
저장소에 두지 않는 것이 원칙이라, 어느 플랫폼이든 이런 창구를 갖고 있습니다.

앱은 아래 순서로 설정을 찾습니다 (`auth/mailer.py:load_email_config`):

**1. Streamlit Community Cloud** — 앱 설정의 `Secrets` 입력란에 `secrets.toml` 내용을
그대로 붙여넣습니다. 플랫폼이 실행 시점에 주입하고, 앱은 평소처럼 `st.secrets`로 읽습니다.

```toml
[email]
provider    = "gmail"
sender      = "myshop@gmail.com"
password    = "앱비밀번호16자리"
sender_name = "Biz Forecaster"
```

**2. Docker · Render · Railway · 회사 서버** — Secrets 입력란이 없으므로 환경변수를 씁니다.

```bash
BIZ_EMAIL_PROVIDER=gmail
BIZ_EMAIL_SENDER=myshop@gmail.com
BIZ_EMAIL_PASSWORD=앱비밀번호16자리
BIZ_EMAIL_SENDER_NAME=Biz Forecaster
```

**3. 로컬 실행** — `.streamlit/secrets.toml` 파일.

세 경우 모두 코드는 그대로입니다. 설정 값이 저장소에 들어가지 않는다는 원칙도 동일합니다.
어느 경로로 읽혔는지는 `check_email.py`가 `설정 출처` 줄에 표시해줍니다.

> 셋 다 없으면 개발 모드로 떨어져 인증코드를 화면에 표시합니다. 배포 후 "메일이 안 온다"면
> 십중팔구 플랫폼 쪽 Secrets/환경변수가 비어 있는 경우입니다.
