# Biz Forecaster - 소상공인 AI 수요예측 및 이상탐지 플랫폼

빵집의 매입장부와 매일 마감 기록 한 줄로 제품별 수요를 예측하고 권장 생산량을 추천하는 Streamlit 앱임.
POS 판매 데이터가 있으면 매출 이상 탐지와 SHAP 기여도 분석도 함께 쓸 수 있음.

## 빠른 실행

Windows에서는 `실행하기.bat`을 더블클릭하면 됨.
Python 탐색, 가상환경 생성, 라이브러리 설치, 앱 실행까지 한 번에 처리함.
첫 실행은 10~30분 걸림(prophet, xgboost 설치). 두 번째부터는 바로 실행됨.

직접 실행할 경우:

```bash
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m streamlit run app.py
```

- Python 3.11 권장. 3.13, 3.14에서는 prophet, xgboost 설치가 자주 실패함.
- 첫 화면에서 회원가입, 이메일 인증, 로그인 후 입력 파일을 업로드함.
- 데이터가 없으면 사이드바의 "동봉된 예시 데이터로 둘러보기"를 체크하면 됨.
- 입력 양식은 사이드바의 "입력 양식 내려받기"에서 받을 수 있음.

## 생산량 추천 동작 원리

POS가 없는 빵집도 쓸 수 있도록 매입장부와 하루 한 번의 마감 기록만으로 동작함.
구현은 `forecast/engine.py`에 단계 순서대로 있음.

1. 매입에서 재료 일소비량 계산. 한 번 산 재료는 다음 매입일까지 고르게 쓴다고 봄.
   예: 밀가루 120kg을 사고 7일 뒤 다시 샀다면 하루 약 17kg 사용.
2. 역레시피로 생산량 추정. 최근 28일 재료 소비량에서 제품별 하루 생산량을 거꾸로 계산함.
   계산이 불안정하면 평소 생산량 구성비 쪽으로 붙잡음(`bom_lambda`).
   여기에 (1 - `prior_waste`)를 곱한 값을 사전값으로 씀.
3. 진짜 수요 복원. 품절 시각과 시간대별 판매 비중으로 품절 뒤에 숨은 수요를 복원함.
   예: 18시까지 하루 수요의 78%가 들어오므로 18시에 30개 품절이면 수요는 약 38개.
   3개가 남았다면 수요는 27개. 보정은 생산량의 2배(`max_uplift`)까지만 인정함.
4. 수준과 요일 계수 학습. 요일 효과를 뺀 뒤 최근 값에 가중치를 더 주는 평균(EWMA)으로 수준을 학습함.
   관측값과 사전값은 n/(n+k) 비율로 섞음. k=5이면 입력 5일에 50:50, 20일에 관측 80%.
   요일 계수도 같은 방식으로, 관측이 적은 요일은 매장 평균 쪽에 무게를 둠.
5. 시즌과 이벤트 보정. 매입 이력이 1년 이상이면 작년 같은 시기의 생산량 변화를 반영함.
   공휴일, 비 같은 이벤트는 설정한 배수를 곱함.
6. 권장 생산량 계산. 목표 서비스수준(품절이 나지 않을 확률) = (판매가 - 원가) / (판매가 - 회수가).
   예: 크루아상(판매가 3,200원, 원가 1,100원, 회수가 0원)은 66%로 빠듯하게,
   다음 날 할인 판매가 가능한 식빵은 95%로 넉넉하게 생산함.

### 입력 변수

| 파일 | 내용 | 입력 주기 | 비고 |
|---|---|---|---|
| `products.csv` | 제품명, 판매가, 원가, 회수가, 평소 생산량 | 1회 | 회수가는 다음 날 할인가 등. 없으면 0 |
| `recipe.csv` | 제품 1개당 주요 재료량 | 1회 | 핵심 재료 2~5개면 충분 |
| `purchases.csv` | 날짜, 재료, 수량 | 과거분 일괄 | 장부, 거래명세서에서 그대로 옮기면 됨 |
| `daily_log.csv` | 날짜, 제품, 결과, (생산량) | 매일 마감 시 | 결과 칸 설명은 아래 참고 |
| `events.csv` | 날짜, 태그 | 선택 | holiday, rain, event |

daily_log.csv 결과 칸 입력 방법:

- `3`: 3개 남음
- `15:30`: 15시 30분에 품절
- `0`: 마감 무렵 다 팔림
- 빈칸: 입력 안 함 (그날은 건너뜀)
- 생산량 칸은 평소와 다르게 만든 날만 입력함.

매일 입력은 제품당 값 하나뿐임. `products.csv` 하나만 있어도 예측이 되고, 나머지 파일이 쌓일수록 정확해짐.
머리글은 영문(product, price 등)과 한글(제품명, 판매가 등) 모두 받음.

### 환경 변수 (Config)

기본값은 `forecast/config.py`에 있고, 앱의 환경 변수 탭에서 바꿀 수 있음.

| 변수 | 기본값 | 의미 |
|---|---|---|
| `open_hour`, `close_hour`, `closed_weekdays` | 8, 21, 없음 | 영업시간과 정기 휴무 요일 |
| `hourly_profile` | 아침, 하교 시간 피크 | 시간대별 판매 비중. 품절 보정 강도를 정하므로 매장에 맞게 조정 |
| `weekday_prior` | 모두 1.0 | 사장님의 요일 감각(예: 토요일 1.2). 초기에 효과가 큼 |
| `alpha` | 0.2 | 높이면 최근 변화에 빨리 반응함. 대신 노이즈도 커짐 |
| `k_cred` | 5 | 관측을 믿기까지 필요한 입력 일수. 낮을수록 빨리 전환 |
| `k_weekday` | 4 | 요일 계수를 보수적으로 잡는 정도. 요일 편차가 과해 보이면 높임 |
| `max_uplift`, `close_uplift` | 2.0, 1.05 | 품절 보정 상한, 마감 직전 품절 시 보정 |
| `loss_rate` | 0.05 | 반죽 손실, 실패, 시식으로 인한 재료 로스 |
| `prior_waste` | 0.10 | 초기 단계에서 생산분 중 안 팔린 비율 가정 |
| `bom_window_days`, `bom_lambda` | 28, 0.3 | 역레시피 계산 기간, 평소 생산 구성비를 믿는 정도 |
| `default_cv`, `sl_bounds` | 0.25, 50~95% | 데이터 부족 시 수요 변동계수, 목표 서비스수준 범위 |
| `event_factors`, `season_bounds` | 공휴일 1.2, 비 0.9, 행사 1.3 / 0.75~1.3 | 이벤트 배수, 시즌 보정 상하한 |

행사(event) 배수 1.3은 설계 문서에 값이 없어 임의로 정한 값임. 매장에 맞게 고쳐서 쓰면 됨.

## 이상탐지 (POS 판매 데이터)

### 화면과 분석을 나눈 이유

관리도, 오탐률 같은 통계 용어는 사장님에게 도움이 안 됨. 같은 계산이라도 받는 사람에 맞게 보여줘야 함.

| 층 | 파일 | 대상 | 내용 |
|---|---|---|---|
| 판단 | `detect/control_charts.py` | 없음 | 통계적으로 이상한지 판단 |
| 번역 | `detect/alerts.py` | 사장님 | 재고를 어떻게 할지 안내 |
| 검증 | `detect/evaluation.py` | 개발자 | 판단을 얼마나 믿을 수 있는지 측정 |

앱 화면에는 통계 용어를 쓰지 않음. 파라미터 조정, 오탐/미탐 채점은 `analyze_detectors.py`로 옮김.

```bash
.venv\Scripts\python.exe analyze_detectors.py
.venv\Scripts\python.exe analyze_detectors.py --save
.venv\Scripts\python.exe analyze_detectors.py --item 크루아상 --magnitude 2.0
```

### 알림이 너무 많아지지 않게 한 장치

1. 20% 미만 차이는 버림. 현장에서 의미 없는 수준이기 때문.
2. 같은 요일끼리 비교함. 전체 평균과 비교하면 주말이 매번 이상으로 잡힘.
3. 이유를 아는 날(시즌, 공휴일, 날씨)은 따로 묶어 아래에 두고, 원인 불명인 날을 맨 위에 올림.

예시 데이터 기준 최근 30일 알림 25건 중 23건이 크리스마스 시즌이었고, 실제 확인이 필요한 건은 2건이었음.

### 관리도 설계

- 관리한계는 전날까지의 값으로만 계산함. 당일 값을 넣으면 이상치가 기준선을 끌어올려 스스로 정상이 됨.
- 요일 패턴을 뺀 잔차로 관리도를 그림. 원래 값으로는 요일 차이 때문에 한계가 넓어져 이상을 놓침.

| 구분 | 3시그마 | EWMA | CUSUM | 다수결 |
|---|---|---|---|---|
| 원래 값 | 7일 | 0일 | 0일 | 3일 |
| 요일 잔차 | 19일 | 21일 | 19일 | 22일 |

### 성능 평가

실제 데이터에는 이상 여부 정답이 없으므로, 크기와 시점을 아는 이상을 일부러 넣고 잡아내는지 측정함.

| 지표 | 뜻 |
|---|---|
| 오탐률 | 정상일 중 잘못 경보한 비율 |
| 미탐률 | 이상일 중 놓친 비율 |
| 실측 ARL0 | 잘못된 경보 한 번까지의 평균 일수 |
| 평균 탐지지연 | 이상 시작 후 처음 탐지까지 걸린 일수 |

예시 데이터에서 다수결 방식의 실측 ARL0는 363으로 이론값(약 370)에 가까웠음.
문턱값을 바꿔도 오탐과 미탐이 동시에 줄지는 않으므로, 어느 쪽 비용이 큰지로 문턱값을 정해야 함.

### 모니터링 연동

탐지 결과는 `monitoring.db`(SQLite)로 저장되며 Grafana에서 바로 읽을 수 있음.

- `daily_metrics`: 일별 값, 관리한계, 방법별 탐지 결과
- `detector_performance`: 파라미터별 오탐/미탐 채점 기록

### 화면에서 뺀 기능

| 기존 탭 | 현재 위치 | 이유 |
|---|---|---|
| 탐지 성능평가 | `analyze_detectors.py` | 개발자용 지표 |
| 품목간 수요연쇄 (H2) | `analyze_item_chain.py` | 가설 검증용, 운영에 불필요 |

```bash

```

## 계정

### 계정 관리

로그인 후 사이드바의 계정 설정 버튼으로 들어감.

| 기능 | 확인 절차 |
|---|---|
| 매장 이름 변경 | 즉시 반영 |
| 비밀번호 변경 | 현재 비밀번호 확인 |
| 이메일 변경 | 현재 비밀번호와 새 주소로 보낸 인증코드 확인 |
| 회원 탈퇴 | 비밀번호와 "탈퇴합니다" 문구 입력 |

탈퇴하면 계정과 업로드 파일(`data/users/<user_id>/`)이 함께 삭제됨.

### 보안

- 로그인한 사용자는 자기 매장 데이터만 볼 수 있음.
- 비밀번호는 PBKDF2-HMAC-SHA256(계정별 salt, 20만 회 반복)으로 저장함.
- 인증코드는 6자리, 10분 만료, 5회 시도 제한, 60초 재발송 대기.
- 로그인 실패 시 "이메일 없음"과 "비밀번호 틀림"을 구분하지 않음.
- 표준 라이브러리만으로 구현함.

### 가입 가능한 이메일

현재 gmail.com 계정만 가입 가능함. Gmail에서 보낸 인증 메일이 다른 서비스에서 스팸으로 분류되는 경우가 많아 제한함.
허용 범위는 `auth/store.py`에서 바꿀 수 있음.

```python
ALLOWED_EMAIL_DOMAINS = ("gmail.com",)              # 현재
ALLOWED_EMAIL_DOMAINS = ("gmail.com", "naver.com")  # 네이버도 허용
ALLOWED_EMAIL_DOMAINS = ()                          # 모든 도메인 허용
```

### 이메일 발송 설정

설정하지 않으면 개발 모드로 동작하며, 인증코드를 메일 대신 화면에 보여줌.

실제 메일을 보내려면 `secrets.toml.example`을 참고해 `.streamlit/secrets.toml`을 만듦.
네이버, 구글 모두 일반 비밀번호가 아니라 앱 비밀번호가 필요함.

```bash
.venv\Scripts\python.exe check_email.py          # 접속, 로그인 확인
.venv\Scripts\python.exe check_email.py --send   # 본인에게 테스트 메일 발송
```

Windows에서는 `이메일설정확인.bat`을 더블클릭해도 됨.

주의: 앱 비밀번호는 받은편지함 읽기 권한도 함께 열리므로 발송 전용 계정을 따로 쓰는 편이 안전함.
폴더를 통째로 복사해 전달할 때는 `secrets.toml`을 먼저 지울 것.

### 배포 시 설정

`secrets.toml`은 저장소에 올라가지 않으므로 배포 환경에서 따로 넣어야 함.
앱은 아래 순서로 설정을 찾음 (`auth/mailer.py`의 `load_email_config`).

1. Streamlit Community Cloud: 앱 설정의 Secrets 입력란에 `secrets.toml` 내용을 붙여넣음.

```toml
[email]
provider    = "gmail"
sender      = "myshop@gmail.com"
password    = "앱비밀번호16자리"
sender_name = "Biz Forecaster"
```

2. Docker, Render, Railway, 회사 서버: 환경변수를 씀.

```bash
BIZ_EMAIL_PROVIDER=gmail
BIZ_EMAIL_SENDER=myshop@gmail.com
BIZ_EMAIL_PASSWORD=앱비밀번호16자리
BIZ_EMAIL_SENDER_NAME=Biz Forecaster
```

3. 로컬 실행: `.streamlit/secrets.toml` 파일.

셋 다 없으면 개발 모드로 동작함. 배포 후 메일이 오지 않으면 대부분 Secrets나 환경변수가 비어 있는 경우임.
